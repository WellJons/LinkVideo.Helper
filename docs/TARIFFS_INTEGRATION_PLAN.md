# LinkVideo.Helper — вкладка «Тарифы»: интеграция нового биллинга

Стадия: **встроены полноценные Qt-экраны поиска, клиента, услуг и диалога смены тарифа с типизированным шлюзом**,
реального API и доступа к данным пока нет. Не считать кнопку открытия кабинета
интеграцией тарифов.

Подтверждённый адрес входа: **https://crm.linkvideo.ru/login**.
На изображении страницы входа видны корпоративные логин/пароль; тип backend,
путь API, схема JWT/session и права API по картинке не определяются.
Автоматический доступ к сайту из среды разработки не получен.

## Назначение

Единая вкладка для сотрудников, где по идентификатору клиента можно
просматривать текущий тариф, стоимость, оплаченный период, задолженность
и историю смены тарифа, **если конкретный источник реально предоставляет эти поля**.
Изменения тарифов — только после проверки прав и явного подтверждения.

Источники внедряются по очереди:
1. **Новый веб-биллинг** — основной приоритет.
2. **КЦ** — отдельный адаптер, если там доступны самостоятельные операции/данные.
3. **«Юля»** — интеграция после уточнения, что именно представляет собой этот источник
   (система, кабинет или другой сервис).

Данные из разных источников нельзя без проверки сливать в один «истинный» тариф.
В интерфейсе всегда указывать источник и время обновления.

## Исследование нового веб-биллинга

Нужно установить официальный URL рабочего кабинета и получить разрешённый способ
интеграции: OpenAPI/Swagger, поддерживаемый внутренний REST/GraphQL API или
согласованный серверный endpoint. Важны:

- метод аутентификации (SSO, служебный токен, сессия, mTLS);
- поиск клиента (номер телефона, ID клиента, камера, договор);
- идентификаторы тарифа, цена/валюта, дата следующего списания, статус;
- права на просмотр и изменение тарифа;
- аудит, rate limits, срок действия сессии, доступность из рабочего VPN;
- тестовый аккаунт и тестовые записи без реальных персональных данных.

Не генерировать URL API и не считать, что публичное наличие веб-страницы
автоматически означает наличие поддерживаемого API.

```text
Helper «Тарифы» (PySide6)
    |
    | HTTPS к LinkVideo internal backend, корпоративная авторизация
    v
LinkVideo Tariffs API (RBAC, rate limit, audit, cache)
    |-- NewBillingAdapter (первый)
    |-- ContactCenterAdapter (позже)
    `-- YuliaAdapter (позже)
    |
    v
Поддерживаемые API каждого источника
```

Helper не должен содержать общего служебного пароля от биллинга.
Серверный backend обязан проверять роль на каждом запросе; скрытая кнопка
не является защитой доступа. Секреты — только в серверном хранилище.

## Проект UI

- Поиск клиента: один общий идентификатор, кнопка «Найти».
- Верхняя карточка: идентификатор, источник, дата актуальности ответа,
  статус запроса — без фальшивого «онлайн» при сбое сервиса.
- «Текущий тариф»: название, цена, период, дата следующего платежа
  и статус — только поля, доступные из API.
- «История»: запрашивается отдельно (ленивая загрузка), если предоставляется.
- «Изменить тариф»: первоначально **отсутствует** до подтверждения API,
  серверных разрешений, политики подтверждений и аудита.
- Отдельное состояние «Источник не подключён», «Недостаточно прав»,
  «Нет данных», «Сервер недоступен» и «Ничего не найдено».
- Не показывать секреты, токены, cookies, полные платёжные реквизиты.

## Получение безопасной карты запросов (локально)

Чтобы установить реальный контракт нового биллинга, сотрудник с
разрешённым доступом входит в `https://crm.linkvideo.ru/login` **в обычном
браузере**, затем открывает нужную страницу тарифов.

1. В Edge/Chrome открыть DevTools → Network → Fetch/XHR и включить
   `Preserve log` перед переходом в тарифы.
2. Выполнить только просмотр/поиск на **тестовой записи**. Не изменять
   оплаченные периоды, тарифы и персональные данные.
3. Экспортировать HAR **локально**. Полный HAR содержит cookies, bearer
   tokens, адреса клиентов и тела запросов: его **нельзя отправлять в чат,
   GitHub или рабочие тикеты**.
4. В корне Helper выполнить:
   `python scripts/inspect_billing_har.py "C:\\path\\to\\billing.har"`
   Скрипт покажет только HTTP-метод, замаскированный маршрут, статус и
   количество запросов; URL/query/headers/body не попадают в результат.
5. Проверить итог на отсутствие конфиденциальных сведений и передать
   **только этот обезличенный список маршрутов** для проектирования API.
   Сам HAR хранить только локально согласно правилам компании и удалить
   после анализа.

Наличие XHR-запросов веб-кабинета не означает, что это поддерживаемый API:
перед интеграцией согласовать стабильность контракта с разработчиками биллинга.
Нельзя выполнять логин через перебор паролей, повторное использование чужой
сессии, копирование cookies или обход серверных проверок.


## Согласованный экран на основе интерфейса CRM (28.10.2026)

Получены скриншоты из корпоративного кабинета:

- Главная страница «Клиенты»: поиск по логину и список недавних клиентов.
- Карточка: статус, тип лица, логин, договор, услуги, баланс.
- Вкладки «Общая информация», «Услуги», «Финансы», «Документы».
- Услуга камеры: имя/ID, тариф, цена, скидка, итог, статус.
- Действия на услуге: смена тарифа, скидка, включение/выключение,
  другие операции и история.
- Изменение тарифа: выбор из **полученных от сервера** тарифов, дата,
  необязательный комментарий и подтверждение.

**В интерфейсе Helper эти экраны уже созданы** в
`linkvideo_vpn_helper/ui/pages/tariffs_page.py`. Сейчас демонстрируются только
надписи «API не подключён» и пустое состояние. Реальные данные будут
поступать через `BillingGateway` из `services/billing_gateway.py`.
Тестовые записи используются только в регрессионных тестах, не в рабочем UI.

Региональный допуск реализован отдельно: биллинг может вернуть клиента только
из `Беларусь` или `Казахстан`. Российские базы не включены, пока нет
отдельного согласованного источника.

Метод получения вариантов тарифа привязан к **ID конкретной услуги**. Все
операции изменения требуют подтверждения, а удалённый адаптер обязан
независимо проверять права и сохранять аудит на сервере. В частности,
нажатие «Тариф» не может изменять все услуги клиента сразу.

Поля финансов и документов, а также действия скидки/отключения/переноса/
истории сейчас не активны, пока не подтверждены их API. Не выдавать
эти заглушки за готовые интеграции.

### Подтверждение авторизации

Пользователь подтвердил, что для нового биллинга используются те же
**учётные данные**, что и в корпоративной админке. Это не доказывает,
что сайт разделяет с ней cookies, токены или механизм REST-авторизации.
Нельзя автоматически пересылать логин/пароль MikroTik, пытаться прочитать
browser cookies или копировать корпоративный пароль в локальный QSettings.
Поддерживаемый вход через SSO или серверный endpoint нужно установить с
разработчиками биллинга.

До появления API backend должен оставаться `UnconfiguredBillingGateway`,
а изменение тарифов — неактивным.


## Установленный контракт: карточка клиента (28.10.2026)

Подтверждено в Network браузера:

- Базовый URL: `https://api-billing-global.linkvideo.ru`
- `GET /api/accounts/{id}` — карточка клиента, ответ 200 OK.
- `GET /api/accounts/{id}/cameras` — запрос списка камер, ответ 200 OK,
  но **тело ответа ещё не изучено**.

Для `GET /api/accounts/{id}` подтверждён формат:
`{"success": true, "response": [{...}]}`, где поля:
`login`, `account_name`, `balance`, `status_name`, `email`,
`phone_number`, `dog_num`, `manager_name`, `registration_date`,
`address`. Примеры аккаунтов, email, идентификаторов и договоров в тестах
вымышленные. **Не коммитить реальные клиентские ответы.**

Парсер `billing_response_parser.parse_account_detail` реализован и
проверяется на санитизированных фикстурах. Он берёт `id` из заранее
доверенного идентификатора запроса, а не из несуществующего поля JSON.
Формат даты `2026-10-13T00:00:00+07:00` выводится как `13.10.2026`.
Код страны **не содержится в этом ответе** и должен быть определён
доверенным источником данных. Валюта баланса также **не указана**.
Отсутствие услуг в этом ответе **не является подтверждением нулевого
числа услуг**.

Что ещё требуется: ответ `/cameras` без реальных логинов, имён и ID
клиентов; запрос поиска по логину, приводящий к ID аккаунта; подтверждённый
механизм авторизации и получение списка тарифов. Нельзя считать работающей
интеграцию без этих контрактов и серверного контроля доступа.


## Подтверждён формат списка камер/услуг (28.10.2026)

Получен скриншот ответа `GET /api/accounts/{id}/cameras`:
`{"success": true, "response": [{...}]}`.

В каждой записи присутствуют:

| Ключ API | Поле Helper |
| --- | --- |
| `id_camera` | ID услуги/камеры в списке, например `901` в тестах |
| `id_camera_vc` | Дополнительный идентификатор камеры; храним отдельно |
| `short_name` | Название камеры |
| `tariff_name` | Название текущего тарифа |
| `ab_plata` | Цена/абонентская плата, без вымышленной валюты |
| `discount` | Значение скидки, единицы измерения ещё неизвестны |
| `costs` | Итоговая стоимость, без вымышленной валюты |
| `status` | Из подтверждённого примера `"1"` соответствует «Активный» |

Статусы, отличные от `1`, пока выводим **как непроверенный код**:
нельзя трактовать `0`/другие значения как «Отключён» без подтверждения.
Нельзя объявлять `discount` процентами — единицы измерения API не указаны.

Реализованы `parse_cameras_response` и `attach_cameras_to_client`
в `services/billing_response_parser.py`. Клиенту выставляется
`services_loaded=True` **только после корректного ответа камер**.
В тестах используются полностью вымышленные данные.

Это завершает отображаемый контракт двух read-only методов по ID.
**Остаются неизвестными**: поиск `login → account ID`, корпоративная
авторизация и refresh, список доступных тарифов для конкретной камеры,
формат запроса смены тарифа и серверная проверка прав.


## Поиск по логину и связывание трёх GET (28.10.2026)

Подтверждено в Network:
`GET https://api-billing-global.linkvideo.ru/api/accounts/search/{query}`
(HTTP 200), ответ
`{"success": true, "response": [{...}]}` с полями:

- `id_account`: внутренний ID для `GET /api/accounts/{id}`;
- `account_name`, `login`: название аккаунта и его логин;
- `balance`, `status_name`: баланс и состояние;
- `services_status`: например, `6/6`; не трактовать как количество
  загруженных записей, показывать отдельно от фактического списка камер;
- `country_name`: **подтверждённый источник страны** для ограничения BY/KZ;
- `account_type_name`: тип клиента (например, «Физическое лицо»).

Разработаны `billing_search_parser.py` и
`billing_readonly_gateway.py`. Композиция в этом порядке:

1. `GET /api/accounts/search/{query}`: безопасно кодировать часть URL,
   выбирать **только точное** совпадение с `login` или `account_name`,
   при нескольких совпадениях не делать произвольный выбор.
2. Убедиться, что `country_name` — «Беларусь» или «Казахстан».
   Если страна не поддерживается, не получать детали или камеры.
3. `GET /api/accounts/{id_account}`: проверить соответствие логина;
   объединить с полями поиска, которых нет в карточке.
4. `GET /api/accounts/{id_account}/cameras`: присоединить услуги
   только к клиенту с подтверждённым ID.

Адаптер **не выполняет реальные запросы по умолчанию**. Он принимает
заранее одобренный, авторизованный `get_json(path)`, которого пока нет в
приложении. До определения поддерживаемой схемы входа/токенов остаётся
`UnconfiguredBillingGateway`. Запись тарифов запрещена.

В тестах используются только фиктивные логины/ID и локальные ответы.
Не передавать в репозиторий реальные значения `Authorization`,
`Cookie`, персональные данные, тела запросов реальных клиентов.

**Дальнейшая задача**: установить разрешённую схему авторизации CRM для
read-only операций и получить методы списка тарифов и смены тарифа
на тестовой услуге, не выполняя её изменения у реального клиента.


## Справочники тарифов, глубины архива и стран (28.10.2026)

В DevTools подтверждены следующие GET-методы:

- `/api/tariffs/list/1`: 87 записей в предоставленном JSON. Возвращаются
  Беларусь, Казахстан **и Российская федерация**; не считать параметр `1`
  кодом страны, его значение неизвестно.
- `/api/cameras/archive-depth/1`: список периодов `id_archive_period`,
  `archive_period_name`, `days`, включая 0 и 180 дней.
- `/api/countries/1`: список стран со значениями `id_country`, `code`,
  `name`, `currency_code`, `prefix_login`. Коды валют из ответа:
  `руб.`, `BYN`, `тг.`.

Структура тарифов: `id_tariff`, `tariff_name`, `description`,
`country`, `account_type_name`, `full_ab_plata`, `is_start`,
`test_days`, `id_tariff_vc`, `count_cameras`,
`start_tariff_lv_monitor`, `is_tariff_lv_monitor`, `is_showed`.

- В JSON встречаются `null` в `count_cameras`,
  `start_tariff_lv_monitor` и `id_tariff_vc`.
- Тарифы Monitor и обычных камер присутствуют в одном списке.
- `is_showed`, `is_start`, `count_cameras` **не доказаны**
  как критерии назначения услуги — их не применяем в роли разрешений.
- `full_ab_plata` не гарантирует месячный платёж (в списке есть тарифы
  оплаты на год). Каталог отображает стоимость из API без утверждений
  о периоде платежа.
- Реально назначаемый тариф отдельной камеры должен быть подтверждён
  сервером биллинга; его нельзя выбирать для записи только по совпадению
  страны/типа.

В `services/billing_catalog.py` добавлены парсеры с проверкой
типов/ID, фильтрация по `client.country` и `client.legal_type`,
получение валюты через справочник стран. В
`BillingReadOnlyGateway.reference_catalog` используется только три
подтверждённых пути. В интерфейсе «Тарифы» добавлен отдельный
**справочный, только для просмотра** диалог: отфильтрованные тарифы,
поиск и вкладка «Глубина архива». В реальном Helper не активируется,
пока не настроена одобренная корпоративная авторизация API. Изменять
тарифы через этот диалог невозможно.

**Следующий недостающий контракт**: URL и метод отправки смены тарифа,
тело запроса, допустимые варианты для конкретной услуги и авторизация
с проверкой прав. Реальные тарифы клиентов не изменять ради исследования.


## Подтверждён POST запроса корпоративной авторизации (28.10.2026)

Из браузера предоставлены Headers / General и Payload успешного входа:

```http
POST https://api-billing-global.linkvideo.ru/auth/login
Content-Type: application/json
```

Форма JSON: `{"login": "<employee-login>", "password": "<password>"}`.
Статус ответа на скриншоте: `200 OK`. **Реальные значения
учётных данных не сохраняются в репозитории.**

Реализован только `services/billing_auth_contract.py`, содержащий
подтверждённый endpoint/метод и типизированную форму запроса; в Helper
**нет автоматического POST**, передачи паролей MikroTik и хранения
секретов CRM.

Для завершения транспортной интеграции нужно выяснить без раскрытия
секретов: возвращает ли `POST /auth/login` токен в JSON (названия полей,
значения скрыть) или `Set-Cookie` в заголовках ответа (только факт
наличия); какими заголовками и с какой формой авторизации идут
последующие `GET /api/accounts/... `. Истечение/обновление сессии и
RBAC также не подтверждены. Не копировать действующие cookies/token
в ChatGPT или исходный код.

Сообщение «одинаковые данные для входа в админку и биллинг»
не доказывает, что тот же пароль подходит к RouterOS: авторизацию
биллинга необходимо хранить и проверять отдельно, а управление
тарифами защищать проверками на стороне сервера.


## Этап самостоятельного входа и общего каталога (28.10.2026)

Сотрудник показал отдельную строку «B2O подключён» и рабочий раздел
**всех тарифов** в CRM. Экран CRM «Все тарифы» при загрузке использует
`GET https://api-billing-global.linkvideo.ru/api/tariffs/list/0` (200 OK).
Отличие параметров `/0` и `/1` по серверным правилам пока не
задокументировано; они используются только как два наблюдаемых пути.

В Helper реализованы:
- `BillingCredentialStore`: отдельная запись `billing/crm` в **том же
  QSettings**, что использует Helper. Только защищённый Windows DPAPI
  пароль; сохранение без шифрования на иных ОС запрещено.
- `BillingLoginPanel`: поля логина/пароля, показ пароля, флажок
  сохранения, очистка и **только явная** кнопка «Взять данные из Helper».
  Никакого автоматического копирования RouterOS-пароля в CRM не происходит.
- `check_billing_login`: явный POST на подтверждённый адрес
  `/auth/login` с `login/password`, отключёнными перенаправлениями,
  таймаутом и выводом **только имён полей** ответа. Ни cookie, ни токены,
  ни ответы с персональными данными не публикуются/не сохраняются.
- `BillingAllTariffsWidget`: постоянная отдельная вкладка «Все тарифы»,
  динамическая загрузка каталога через `BillingReadOnlyGateway.all_tariffs`,
  поиск и фильтрация страны. Кнопки изменения тарифа отсутствуют.
- Тесты на подставных данных проверяют разделение секретов,
  шифрование, отказ невалидного входа, возвращаемые поля без
  секретов и обновление каталога при появлении нового тарифа.

**Граница готовности:** live POST входа можно отправить только по
действию сотрудника. Полученный HTTP 200 не приравнивается к
установленной защищённой сессии, поэтому производственный
`UnconfiguredBillingGateway` по-прежнему блокирует чтение/изменение
данных. Для завершения нужен безопасный контракт **ответа**
`POST /auth/login` (названия полей, без содержимого токенов) и
авторизации последующего GET (заголовки без значений). Только после
этого подключать авторизованный transport к готовым GET.


## Подтверждён JSON-ответ успешного входа

После `POST /auth/login` браузер получает
`{"token": "<secret>"}`. Значение токена в PR не копируется.

Теперь форма Helper:
- показывает «Войти» вместо кнопки простого теста;
- принимает подтверждённый вход только при HTTP 2xx и непустом
  строковом поле `token`;
- держит токен **только в оперативной памяти** открытой формы;
- имеет «Выйти» (локально удаляет токен из памяти, серверный logout
  endpoint пока неизвестен) и «Очистить данные»;
- после изменения логина/пароля инвалидирует текущий токен;
- сохраняет пароль отдельно через Windows DPAPI только при опции
  «Запомнить», никогда не записывает токен в QSettings.

**Важно**: это уже настоящее получение токена при явном входе, но
API-подключение к клиентам пока не включено. Для его включения ещё
требуется подтвердить, отправляет ли браузер в защищённых GET
`Authorization: Bearer <token>`, `token: <token>` или другой
заголовок. Нужны лишь **имя заголовка** и наличие `Bearer`, но ни
сама строка токена, ни cookies передаваться не должны.

Автоматическая перепроверка при истечении токена и серверный revoke
также останутся отдельными этапами.


### Подготовлен защищённый транспорт для последующих GET

`BillingTokenTransport` поддерживает только заранее подтверждённые
read-only URL поиска/карточки/камер/тарифов. При создании не выбирается
заголовок автоматически: режим `token`, `authorization_bearer` или
`authorization_raw` задаётся **только после подтверждения того,
что браузер действительно отправляет его на API**.

При отсутствии подтверждённого режима все запросы отклоняются до выхода
в сеть. Токен не выводится в `repr`, не передаётся через URL, не
сохраняется в настройках; `close()` очищает локальный токен. При
401/403 не выполняется автоматическая отправка пароля — сотрудник
должен повторно подтвердить вход. Реальная связка токена с GUI и
read-only gateway активируется после подтверждения заголовка.

## B2O: создание клиента и выдача реквизитов (28.10.2026)

Подтверждён успешный `POST /ords/mobile/vc2/operators/241/clients`
с семью полями: `account_type` (строка `"1"`),
`client_name`, `login`, `password`, `phone`,
`push_to_billing` (число `1`), `cross_sharing_enabled` (число `0`).
Ответ: HTTP 200, JSON с положительным `id_account`.
Контрольный GET по `/operators/241/clients/{id_account}` возвращает
идентификатор и логин клиента. Этого недостаточно для утверждения,
что синхронизация с отдельной CRM уже завершена.

В Helper операция активна только для проверенного сочетания:
Россия (оператор 241), тип `"1"`, включён «Завести в биллинг»,
выключен общий доступ между операторами. Реальные пароли и токены
в исходники и тестовые фикстуры не переносились. Перед POST сотрудник
подтверждает операцию. Автоматически повторять неясно завершившийся
POST нельзя: клиент мог быть создан.

После подтверждённого `id_account` GUI показывает отдельный блок
с редактируемым только через исходную форму набором реквизитов:
`Создали вам аккаунт:`, логин, пароль, напоминание о смене данных
после входа. В блоке есть кнопка «Скопировать данные» — текст попадает
в буфер обмена **только по нажатию**. Пароль берётся из снимка формы,
отправленного именно этим POST (даже если поля позднее изменились).
Рядом с паролем есть генератор на `secrets` и переключатель видимости.
Блок появляется только после подтверждённого успешного создания.
В одной открытой форме Helper успешные или неопределённые отправки
того же логина блокируются даже после переключения на другой логин
и обратно.

### Дополнительные наблюдения: удаление и поиск

Другой скриншот фиксирует `DELETE
/ords/mobile/vc2/operators/241/clients/320725` с HTTP 200
и телом `{"status":"ok"}`. После этого запрос списка
`GET /ords/mobile/vc2/operators/241/clients` вернул структуру
`{"count":50,"page":1,"total":0,"search":"<query>","data":[]}`.
Пустой результат поиска согласуется с удалением, но не доказывает
отсутствие записей по другим запросам или глобальную очистку.

**DELETE в Helper не реализован:** операцию нельзя запускать
автоматически при создании или в целях тестирования. При добавлении
проверяется только подтверждённый POST.
