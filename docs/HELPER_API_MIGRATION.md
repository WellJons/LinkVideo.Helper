# LinkVideo.Helper: постепенный переход на внутренний API

Статус: **план, не реализовано**. Этот документ не разрешает открывать RouterOS API,
PostgreSQL или служебные ключи в Интернет.

## Фактическое исходное состояние

- Desktop Helper напрямую обращается к RouterOS API для поиска и изменения VPN-клиентов.
- В репозитории есть прототип `scripts/vpn_sync_agent.py`, который периодически
  переносит данные RouterOS в Google Sheets. План PostgreSQL описан отдельно в
  `docs/VPN_DATA_BACKEND.md`.
- Настройки рабочей версии могут содержать адрес сервиса VPNsync с PostgreSQL,
  но его исходники, реальная схема БД, механизм входа и точные endpoints нужно
  отдельно инвентаризировать, прежде чем считать его готовым публичным backend.
- Существующие локальные RouterOS-креды и политики ролей не являются полноценной
  серверной авторизацией.

## Целевая архитектура

```text
LinkVideo.Helper (PySide6)  ─┐
                            ├── HTTPS, versioned REST API ── LinkVideo API
Веб-кабинет операторов ─────┘                         │
                                                  RBAC + audit
                                                      │
                                             PostgreSQL (read model)
                                                      ↑
                                                VPNsync/worker
                                                      │
                                               private network
                                                      │
                                               RouterOS VPN fleet
```

- Веб-приложение и desktop обращаются к одному backend API, не к базе напрямую.
- Backend проверяет сессию, роль и разрешённые действия **для каждого запроса**.
- RouterOS API доступен только backend/worker по приватной сети/VPN, а не
  публикуется наружу; секреты хранятся на сервере в защищённом хранилище.
- PostgreSQL хранит поисковую модель, изменения и `last_synced_at`; значение
  «онлайн» не выдаётся за текущее состояние при устаревшей синхронизации.
- Долгие операции выполняются через фоновые задачи со статусом операции, а не
  блокируют HTTP-запрос или Qt event loop.
- Сервис за HTTPS (на внутреннем домене и/или через корпоративный VPN), с
  журналом операций и резервными копиями. Не копировать пароли в логи.

## План миграции

1. **Инвентаризация**: проверить реальный VPNSync-сервер/порт, API, схему
   PostgreSQL, резервные копии, авторизацию и сетевой доступ. Описать ownership.
2. **Read-only API** с OpenAPI-контрактом:
   `GET /api/v1/health`,
   `GET /api/v1/vpn/servers`,
   `GET /api/v1/vpn/clients?query=...`,
   `GET /api/v1/vpn/clients/{id}`.
   Не отдавать PPP-пароли в списках; использовать cursor pagination и показывать
   `last_synced_at`/состояние источника. Нужны лимиты и индексы БД.
3. **Клиентский адаптер** в Helper:
   `VPNRepository` с реализациями `DirectRouterOS` и `RemoteAPI`;
   переключение источника поиска за feature flag, автоматизированные тесты
   совпадения результатов, явная диагностика недоступного API.
4. **Безопасная идентификация**: корпоративная авторизация (OIDC/SSO либо
   отдельный надёжный IdP), серверный RBAC «сотрудник / системный администратор»,
   короткоживущие токены, аудит и отзыв доступа. Не считать логин с суффиксом
   доказательством роли.
5. **Мутации через backend**: создание/изменение VPN/NAT как задачи
   `POST /api/v1/operations` с idempotency key, preflight-проверками и
   журналированием. Проверки прав и конфликтов на стороне backend.
6. **Веб-интерфейс** подключать к тому же API после стабилизации read-only
   запросов; desktop остаётся рабочим параллельно. Убирать прямые RouterOS
   подключения постепенно и только после приемочных испытаний.

## Первые проверки безопасности/качества

- Не хранить пароль RouterOS в открытом виде в настройках клиента (текущая
  схема `QSettings` требует отдельного рефакторинга на Windows Credential
  Manager/DPAPI до массового внедрения).
- Защитить методы изменения клиентов на backend от обхода UI/RBAC.
- Измерить p50/p95 время поиска и создания клиента на реальной сети, добавить
  request IDs, отдельные timeout/retry и подробные сообщения в UI.
- Зафиксировать тесты: ошибочный вход, сбой API, недоступность одной ноды,
  устаревшие данные, отсутствие прав, повтор запроса на создание, конфликт NAT,
  откат после неудачного частичного изменения.
